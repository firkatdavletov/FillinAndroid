# Дневной лимит и планирование доходов v1

Android реализует локальный расчёт. Для облачных бюджетов до выпуска Android требуется
реализация этого контракта в FinanceConsultante. Production-развёртывание этим изменением
не выполняется. Базовый протокол остаётся budget-scoped HTTP v4, Firebase, текущие receipts,
requestId, revisions, пагинация и атомарная публикация snapshot.

## Согласование возможностей

Ответ чтения бюджета должен включать `dailyLimitPlanningV1` в capabilities. Android передаёт
`X-Fillin-Capabilities: confirmedPlanLinkingV1,dailyLimitPlanningV1` и проверяет возможность
перед отправкой новых команд. Без неё команды сохраняются в outbox и обмен останавливается
с `backend_update_required`. Это также относится к ссылкам на регулярные доходы.
Сохранённые UUID, wirePayload и receipts прежних команд не переписываются.

Первое принятие новой команды атомарно активирует новую модель бюджета. После активации
сервер требует обе возможности от всех участников (426 `client_upgrade_required` при
отсутствии), чтобы старый клиент не возобновил автоматическое ожидание частичного остатка.
Уже принятый requestId возвращает сохранённый receipt после проверки доступа, до проверки
новых требований к клиенту. Отсутствие capability не означает разрешение игнорировать поля.

## Правила и вхождения

Новый sync kind `INCOME_RULE` использует обычный `record`:

```json
{
  "id":"UUID правила", "categoryId":"UUID категории", "amount":"300000.00",
  "dueOn":"2026-11-15", "incomeName":"Зарплата", "incomeActive":true,
  "incomeFrequency":"MONTHLY", "status":"SCHEDULED", "version":0,
  "createdAt":"2026-11-01T00:00:00Z", "modifiedAt":"2026-11-01T00:00:00Z"
}
```

Периодичность: ONCE, WEEKLY, BIWEEKLY, MONTHLY. `dueOn` правила — опорная дата;
недельные интервалы 7/14 дней от неё, месячные даты независимо ограничиваются длиной месяца.
31 января → последний день февраля → 31 марта. Для простого разового дохода сохраняется
`EXPECTED_INCOME`, без отдельного правила, с дополнительными incomeName/incomeActive.

Каждое регулярное поступление — `EXPECTED_INCOME` с собственными id/version и полями
`ruleId`, `scheduledOn` (исходная дата в серии), `dueOn`, amount, incomeName, incomeActive.
Идентичность `(ruleId, scheduledOn)` неизменна при переносе ожидаемого остатка.
Для ещё не материализованного события обе стороны получают UUID через Java
`UUID.nameUUIDFromBytes(UTF8("income:" + ruleId + ":" + ISO_DATE))`:
MD5 этих байтов, выставить version=3 и RFC 4122 variant; дополнительного namespace нет.
Сервер должен соблюдать уникальность пары и UUID. Версия нового вхождения 0.

Команды `CREATE_INCOME_RULE`, `UPDATE_INCOME_RULE`, `DELETE_INCOME_RULE` используют стандартный
конверт commands и перечисленные поля. UPDATE передаёт полный план: categoryId, amount,
dueOn, incomeName, incomeFrequency, incomeActive. expectedToken относится к правилу.
DELETE помечает правило CANCELLED; фактические операции и ссылки сохраняются.
Редактирование меняет только будущие неподтверждённые события; полученные суммы и история
сохраняются. Невошедшие в новое расписание будущие неоплаченные вхождения отменяются.
Выключение исключает серию из прогноза, включение восстанавливает действующее расписание.
Права создания и изменения планов остаются OWNER.

Преобразование прежнего разового дохода в серию: UPDATE_INCOME_RULE с прежним ID атомарно
создаёт правило и сохраняет старый EXPECTED_INCOME как первое вхождение с прежним ID и
связями, добавляя ruleId/scheduledOn. Для этой пары существующий ID имеет приоритет над
детерминированным UUID. INCOME_RULE и EXPECTED_INCOME могут иметь одинаковый ID в разных kind.
Это не создаёт повторное первое поступление. Android не требует физической миграции Room:
новые записи используют существующую таблицу budget_sync_records.

## Связь и частичные поступления

Существующий подтверждаемый механизм из backend-operation-plan-linking.md сохраняется.
Для INCOME `PlanLinkTarget` дополнительно передаёт ruleId и scheduledOn, когда это серия;
planId остаётся ID вхождения, dueOn — его исходная ожидаемая дата. Сервер материализует
необходимое вхождение атомарно перед проверкой связи. expectedPlanVersion относится именно
к вхождению, не к правилу. Ссылки одного поступления на несколько операций разрешены;
автоматического создания проводок или автоматического сопоставления нет.

Полностью полученный доход исключается из прогноза. Частично полученный также исключается,
пока пользователь не подтвердил остаток. Для подтверждения:

```json
{
  "requestId":"UUID", "householdId":"UUID", "memberId":"UUID",
  "type":"CONFIRM_REMAINDER_INCOME", "entityId":"UUID вхождения",
  "authoredOn":"2026-11-15", "expectedToken":0,
  "ruleId":"UUID правила", "scheduledOn":"2026-11-15",
  "remainderAmount":"100000.00", "remainderDueOn":"2026-11-17",
  "remainderReceived":"200000.00"
}
```

ruleId/scheduledOn отсутствуют для разового дохода. Сумма положительная, не больше
неполученной части, максимум два десятичных знака; дата не в прошлом. remainderReceived
должен точно совпадать с текущей суммой фактических связанных поступлений; иначе конфликт.
Успех увеличивает версию вхождения и возвращает receipt. Эти три remainder-поля сохраняются
в EXPECTED_INCOME и синхронизируются другим участникам. `dueOn`, scheduledOn и расписание
не меняются. Любое изменение суммы связанных поступлений делает подтверждение неактуальным,
пока пользователь не подтвердит его заново. Снятие связи восстанавливает соответствующую
часть плана; при нулевой полученной сумме применяется обычная дата планового дохода.

Новые команды и связи зависят от создания правила/категории/операции в outbox. Повторы
идемпотентны, другой payload с прежним requestId конфликтует. Семейные гонки проверяются
на сервере транзакционно. Tombstone не должен удалять фактическую проводку или создавать
её повторно. Изменения правил, вхождений и связей публикуются в одном snapshot revision.
Локальная загрузка бюджета сохраняет все команды без переписывания payload; они отправляются
после bootstrap только совместимому серверу.

## Расчёт и проверки выпуска

Баланс — фактические POSTED операции с локальными изменениями. Будущий доход не меняет его.
Доход доступен со следующего календарного дня; просроченное неполученное вхождение исключено,
будущие вхождения остаются. Неоплаченные обязательства, включая архивные категории,
учитываются остатком, просроченные — сегодня. Расчёт в KZT/Asia/Almaty, резерв MVP 0.

Окно заканчивается перед первым доходом с датой today+30…today+60; иначе включает сегодня
и ещё 59 дней. В каждой дневной точке проверяется платёжеспособность, выбирается минимальное
ограничение, лимит округляется вниз до целого тенге. Внутридневные повседневные траты и
возвраты восстанавливаются при определении ориентира, но не при проверке дефицита.

До выпуска проверить миграцию старых разовых доходов без изменения ID и ссылок; частичное
поступление без/с подтверждением и после изменения суммы; 31-е число; пропущенную зарплату;
раннюю оплату; двух участников; lost response, повторы UUID; многостраничный snapshot;
выключение/удаление серии; загрузку LOCAL→CLOUD; запрет старым клиентам после активации.
Контрольные примеры: 5681 KZT на 44 дня до 14 декабря и 5806 KZT на 31 день до 28 ноября.
