# Firebase Authentication: этапы внедрения

## Порядок приёмки

Каждый этап заканчивается установленной на устройство сборкой и отчётом о проверках.
Следующий этап начинается после приёмки предыдущего. Production-развёртывание выполняется отдельно.

## Принятые решения

- Локальный режим не требует Firebase, аккаунта и интернета.
- Вход в облако — через Google и Firebase Authentication.
- У одного аккаунта может быть несколько собственных и семейных облачных бюджетов.
- Данные, очереди и роль пользователя изолированы по бюджету.
- После выхода облачные данные скрыты, но сохранены до повторного входа тем же аккаунтом.
- Фоновая синхронизация работает только для выбранного облачного бюджета текущего UID.
- Семейное приглашение — одноразовый код на 24 часа; новый код отменяет предыдущий.
- Реальные проверки выполняются с тестовым сервером и двумя Google-аккаунтами.

## Контракт целевого API

- `POST /api/v4/auth/firebase`: проверка ID token и профиль пользователя по UID.
- `GET /api/v4/budgets`: доступные бюджеты с названием и ролью.
- `POST /api/v4/budgets`: создание бюджета и OWNER по Firebase с постоянным requestId.
- `POST /api/v4/budgets/import`: исходный bootstrap локального бюджета; история передаётся очередью v4.
- `/api/v4/budgets/{budgetId}/…`: чтение, синхронизация и участники выбранного бюджета.
- Уточнение пользователя от 2026-10-21: поддержка HTTP API v1–v3 не требуется.
  Firebase-подключение использует только v4; существующие v4 payload/requestId сохраняются.
  Сервер определяет BudgetActor по проверенному Firebase UID и budgetId из пути.
- Собственный серверный JWT не выдаётся.

## Проверки при завершении

- Android: unit-тесты, instrumentation-тесты и debug-сборка.
- FinanceConsultante: `test`, `check`, `bootJar`; миграции PostgreSQL и сохранение финансового авторства.
- Реальный Google-вход проверяется отдельно от fake-verifier и Firebase Auth Emulator.
- Ни установка SDK, ни успешный тест локального бюджета не означают реализацию T02–T12.
