# Saldomi 0.1. Доступ к облачным функциям

Статус — спецификация для реализации в FinanceConsultante.

Saldomi 0.1 открывает локальный бюджет без обязательной авторизации. Android разрешает облачные функции установкам из списка backend. Единственный автоматический запрос обычной установки проверяет доступ и не содержит финансовых данных. Ограничение в два локальных бюджета проверяет Android.

## Проверка доступа

`GET /api/v4/app/access` доступен без Firebase-токена. Android посылает `X-Device-Id` с UUID установки и `X-App-Version` со строкой версии, например `0.1`. UUID сохраняется при обновлении приложения. После переустановки или очистки данных пользователь копирует новый ID из раздела «О приложении».

| Условие | HTTP | JSON |
| --- | --- | --- |
| Активная запись для ID | 200 | `{"mode":"INTERNAL_FULL"}` |
| Корректный UUID отсутствует в списке или отозван | 200 | `{"mode":"OFFLINE_FREE"}` |
| Заголовок ID отсутствует, повторяется или содержит неканонический UUID | 400 | `{"code":"invalid_device_id"}` |

Ответ JSON содержит `Cache-Control: no-store`. Приложение хранит последнее подтверждённое разрешение в своей установке. Успешный `OFFLINE_FREE` и облачный `device_access_denied` снимают это разрешение. Ошибка сети, неуспешный ответ проверки и неизвестный режим оставляют последнее подтверждённое состояние. Версия используется для диагностики. Решение принимается по UUID и активности записи.

## Список установок

Добавить Flyway-миграцию с таблицей `internal_app_installation`. Достаточно полей `device_id UUID PRIMARY KEY`, `active BOOLEAN NOT NULL`, `label TEXT NOT NULL`, `updated_at TIMESTAMPTZ NOT NULL`. Служебная подпись помогает оператору отличать установки, например «Тестовый Pixel». Миграция создаёт пустой список.

Добавление или повторное разрешение выполняется оператором через параметризованный SQL:

```sql
INSERT INTO internal_app_installation (device_id, active, label, updated_at)
VALUES (:device_id, TRUE, :label, CURRENT_TIMESTAMP)
ON CONFLICT (device_id) DO UPDATE
SET active = TRUE, label = EXCLUDED.label, updated_at = CURRENT_TIMESTAMP;
```

Отзыв:

```sql
UPDATE internal_app_installation
SET active = FALSE, updated_at = CURRENT_TIMESTAMP
WHERE device_id = :device_id;
```

Применять изменение к следующему запросу после фиксации транзакции. UUID передавать по приватному каналу. Ограничить служебные логи кодом отказа и версией приложения. UUID установки — метка для выдачи функций. Облачные данные по-прежнему защищают Firebase ID token, принадлежность к бюджету и роль.

## Ограничение облачных API

После включения `INTERNAL_DEVICE_GATE_ENABLED` общий фильтр облачных API проверяет активный UUID на каждом запросе. Отсутствующий, неверный, неизвестный или отозванный ID получает HTTP 403 с телом `{"code":"device_access_denied"}`. Проверка выполняется до бизнес-операции, включая повтор команды с сохранённым receipt. При недоступности таблицы сервер возвращает 503. Отзыв действует на последующие запросы. Уже принятая команда может завершиться, а её повтор после возвращения доступа сохраняет прежнюю идемпотентность.

Фильтр охватывает подтверждение серверного профиля `/api/v4/auth/firebase`, каталог и создание бюджетов, импорт, данные и sync бюджета, управление бюджетом, приглашения и участников. Проверка доступа, создание запроса на удаление существующего аккаунта и опрос статуса удаления доступны отдельно. Удаление сохраняет действующие проверки Firebase и повторного подтверждения, включая текущий контракт опроса статуса. Регистрация и вход через Firebase SDK управляются самим Firebase. Фильтр FinanceConsultante охватывает API приложения.

## Порядок выпуска и приёмка

1. Выпустить миграцию и endpoint с выключенным фильтром, зарегистрировать тестовые ID.
2. Проверить сборку 0.1 с известным, неизвестным и новым ID после переустановки. Проверить отказ и возврат доступа без перезапуска приложения.
3. Включить фильтр на тестовом сервере. Проверить каждый облачный маршрут с активным и отозванным ID, без ID, с неверным токеном и с токеном пользователя другого бюджета. Проверить исключения для endpoint доступа и удаления аккаунта.
4. Выпустить сборку 0.1 и включить фильтр в production после проверки своих установок. Клиенты без ID после включения теряют облачный доступ. Фильтр можно отключить отдельно от endpoint и таблицы.
5. Проверить, что запросы отозванной установки не меняют бюджет, членство и receipts. После возврата доступа повтор ранее принятой команды должен вернуть прежний receipt. Удаление существующего аккаунта должно завершаться при отозванном ID.
