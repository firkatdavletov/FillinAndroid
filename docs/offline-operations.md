# Offline-first операции

## Локальная модель

`feature/operationhistory/data/local` содержит Room-базу версии 1 с экспортированной
схемой. Денежные значения сохраняются строками и рассчитываются через `BigDecimal`.
База отделена по URL backend. Записи, категории и очередь привязаны к household/member.
Смена области при синхронизации блокирует отправку прежней очереди, сохраняя данные.

`local_operations` содержит канонические серверные проводки всех направлений и локальные
`PENDING`/`REJECTED` операции. `local_categories` сохраняет также архивные категории для
истории. `operation_outbox` содержит неизменяемый сериализованный запрос и UUID.
`operation_sync_state` хранит курсор, ревизию, параметры области и состояние загрузки.

`OperationHistoryStore` предоставляет наблюдаемые историю и контекст. UI не использует
сетевой ответ как второй источник списка. Первая загрузка и каждая применяемая страница
сохраняются вместе с курсором одной транзакцией. Неполный срез не выдаётся за полный.

## HTTP

`POST /api/v1/operations` принимает `requestId`, ожидаемые `householdId`/`memberId`,
`type` (`EXPENSE`/`INCOME`), `categoryId`, десятичную строку `amount`, `currency=KZT`,
`occurredOn` и необязательное `description`. Возвращает `requestId` и `operation`.
Повтор принятого UUID с теми же параметрами возвращает текущее состояние той же проводки;
иной payload возвращает `409 idempotency_conflict`. Область проверяется до финансовой записи.

`GET /api/v1/sync/changes?cursor=...` возвращает `scope`, `changes`, `nextCursor`, `hasMore`.
Первый запрос не передаёт курсор. Курсор непрозрачен клиенту и привязан к household/member.
Каждый срез имеет фиксированную верхнюю ревизию. Курсор последней страницы начинает новый
срез при следующем запросе. Журнал содержит backfill существующих данных и дальнейшие
снимки `LEDGER`/`CATEGORY`, включая отмены, возвраты и архивирование. В первой версии
журнал хранится без очистки.

Денежные поля sync-снимка — десятичные строки: `originalAmount`, `originalCurrency`,
`amountKzt`. Также передаются `id`, `categoryId`, `type`, `occurredOn`, `createdAt`, `status`,
`version`, `sequence`, `description`, `refundOf` и доступный текущему участнику `requestId`.
Внутренние source key и audit snapshot в API не раскрываются.

## Доставка и восстановление

Один `OperationsSynchronizer` сериализует pull → push → pull через mutex. Если после
первого pull очередь отправки пуста, синхронизация завершается без второго pull.
Первый pull по-прежнему загружает все страницы; после отправки локальных операций
повторный pull сохраняется. WorkManager добавляет уникальные последовательные задания
с `APPEND_OR_REPLACE`, поэтому сохранение во время завершения worker не теряет сигнал.
Курсор и очередь переживают остановку процесса;
запуск приложения повторно обнаруживает неотправленные записи. Android может отложить
фоновые задания; точное время доставки не гарантируется.

При наличии сети планировщик сразу начинает попытку в процессе приложения. Её результат
связан с UUID задания WorkManager: worker ожидает ту же попытку или забирает её готовый
результат, не запуская второй обмен. После ошибки следующая попытка worker выполняет
обмен заново с backoff. После остановки процесса worker выполняет обычную синхронизацию.
Автоматический запуск при старте и возвращении приложения выполняется через `onStart`
жизненного цикла процесса; создание ViewModel истории не дублирует этот запрос.

При потере ответа следующий pull находит операцию по `requestId`, сопоставляет локальную
строку с серверной и завершает запрос атомарно. Повторный POST с прежним UUID также безопасен.
Более старая серверная версия не перезаписывает уже полученную новую.

Сетевые ошибки, `429`, `5xx` и некорректный ответ сохраняют запрос для повтора.
`401`/`403` и конфликты приостанавливают отправку. Только подтверждённые `400`/`422`
с кодом валидации переводят строку в `REJECTED`. Неоднозначный результат не разрешает
редактировать payload или автоматически подменять UUID.

Обычное удаление данных приложения или удаление приложения удаляет ещё не отправленные
локальные записи. Room не использует destructive migration; при изменении схемы требуется
явная миграция с сохранением очереди.
