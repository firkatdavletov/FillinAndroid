# T12 — завершение перехода на Firebase

## Что меняется

Android больше не читает MOBILE_API_TOKEN из local.properties и не создаёт такого
поля BuildConfig. У облачных профилей единственный рабочий сетевой путь — Firebase
ID token текущего UID и адресные endpoints /api/v4/budgets/{budgetId}/….
Собственный JWT не используется. После 401 выполняется одно обновление Firebase-токена.

Локальные и прежние LEGACY-профили получают транспорт, который останавливает запрос
до сети и предлагает Google-вход. Создание локального бюджета и работа без интернета
сохраняются. Подключение выполняется через «Подключить к аккаунту» либо выбор бюджета
Google-аккаунта. Подсказки о настройке статического токена заменены сообщениями о входе.

FinanceConsultante не читает MOBILE_API_TOKEN. Даже оставленный app.mobile-api.token
не восстанавливает доступ: прежние unscoped endpoints v1–v3, GET /api/v4/budget,
POST /api/v4/legacy/budgets и /api/v4/sync/… отклоняют авторизацию. Актуальные
Firebase endpoints не имеют fallback на прежний секрет. Поддержка v1–v3 снята по
уточнению пользователя от 2026-10-21.

## Данные и очереди

Новой миграции SQLite или PostgreSQL нет: реестр Android остаётся v5, финансовая база
v4, сервер — Flyway V27. UUID, имена файлов, история, requestId, intent и wirePayload
не переписываются. Старые строки mobile_budget_access и финансовые receipts остаются
для сохранности прежних данных, но не являются действующей авторизацией.

Существующие v4-команды отправляются через Firebase с прежним payload/requestId.
Транспортный адрес содержит budgetId, сервер проверяет BudgetActor по UID и бюджету.
Очереди v1–v3 не преобразуются, не отправляются и не удаляются; неподдерживаемый
формат останавливает подключение с понятной ошибкой.

BuildConfig.API_BASE_URL сохраняет прежнее значение для обнаружения исторического
файла operations-<hash>.db. Менять его ради нового сервера нельзя: фактический backend
Firebase задаётся FIREBASE_API_BASE_URL. Прежние Retrofit API не регистрируются как
рабочий транспорт production-графа; старые адаптеры остаются только для изолированных
тестов исторического формата и не получают credentials приложения.

## Настройка и выпуск

1. Сохранить резервную копию серверной БД и данных устройства. Проверить восстановление
   в отдельном хранилище и прежние UUID/очереди.
2. Собрать сервер T12 с V27 и включить MOBILE_API_ENABLED=true, FIREBASE_AUTH_ENABLED=true,
   FIREBASE_PROJECT_ID и GOOGLE_APPLICATION_CREDENTIALS. JSON service account находится
   вне репозитория и Android APK. Новых credentials для T12 нет.
3. Сначала обновить тестовый сервер. Старую переменную MOBILE_API_TOKEN можно оставить
   на время обновления: новый JAR её игнорирует. После проверки удалить переменную
   в Railway. Удаление секрета из окружения до обновления старого JAR может остановить
   прежний сервер на проверке конфигурации.
4. Проверить на обновлённом сервере: старый Bearer даёт 401; Firebase ID token получает
   профиль и список только своих бюджетов. Никаких raw tokens в логи или команды отчёта.
5. В Android задать HTTPS FIREBASE_API_BASE_URL либо оставить сервер по умолчанию.
   Установить новую debug-сборку через install -r. local.properties может содержать
   только нужные SDK/серверные настройки, прежний MOBILE_API_TOKEN удалить.
6. Перед release зарегистрировать SHA-1/SHA-256 реального signing certificate в Firebase,
   проверить Google provider, package ID и google-services.json. assembleRelease создаёт
   APK, но не подтверждает подпись выпуска и вход с release-сертификатом.
7. После приёмки тестового сервера выполнить production-развёртывание отдельной задачей.
   В этой работе автоматического deploy или push нет.

Для старого бюджета, ещё не связанного с Firebase, настроить точную пару
FIREBASE_LEGACY_UID / FIREBASE_LEGACY_MEMBER_ID. Email не является основанием доступа.
MemberId берётся из доверенной прежней базы или её приватной копии. Опциональный
prepareLegacyBinding теперь экспортирует cached ID после подтверждения Google UID
через Firebase и не обращается к статическому API; сервер проверяет членство отдельно.

## Приёмка

Автоматический сквозной FirebaseTransitionDeviceTest использует изолированные базы
и синтетические аккаунты: локальный расход → импорт с прежними UUID → второй бюджет
и его очередь → семейный MEMBER и общий расход → выход/другой UID → возвращение
исходного профиля и отправка только его очереди. Старый секрет в этом пути отсутствует.

Ручной путь на двух устройствах после обновления тестового сервера:

1. Создать локальный бюджет в авиарежиме, добавить операции.
2. Включить сеть, войти через Google и выбрать «Подключить к аккаунту».
3. Создать второй облачный бюджет, проверить отдельные балансы и переключение офлайн.
4. В первом бюджете создать приглашение; вторым Google-аккаунтом на другом устройстве
   вступить, добавить расход и получить его на первом устройстве.
5. Оставить изменения офлайн, выйти, войти другим аккаунтом и вернуться исходным.
   Проверить, что данные скрывались и восстановились, повтор обмена не меняет деньги.
6. Проверить отказ прежнему токену на обновлённом тестовом сервере.

Google UI и настоящий Firebase проверяются отдельно от fake API; live-тесты на текущей
Google-сессии не заменяют полную ручную приёмку двумя аккаунтами и новым release certificate.

## Результаты

- Android :app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest
  :app:assembleRelease — успешно. 242 unit-теста без ошибок и пропусков.
- Debug, androidTest и release APK проверены на отсутствие прежнего значения секрета;
  в рабочих APK также нет поля/строки MOBILE_API_TOKEN. Устаревшая запись удалена
  из local.properties без вывода её значения. Release APK unsigned, на Pixel установлен debug.
- Полный Pixel-прогон: OK (156 tests), 153 успешных и 3 пропущенных opt-in live-проверки.
  Успешны новый сквозной тест T12 и все 20 тестов навигации.
- Отдельно с liveFirebaseAuth=true прошли оба теста текущей реальной Google-сессии:
  повторный профиль того же серверного пользователя и управляемый 401 с настоящим
  forceRefresh Firebase SDK. Выполнялись профильные запросы, без финансовых записей
  на развёрнутом сервере. Этот сервер отдельно не обновлялся до кода отключения токена;
  отказ старому токену проверяется локальным серверным PostgreSQL/HTTP набором.
- Сервер test/check/bootJar — успешно: 315 unit и 232 integration без ошибок/пропусков;
  ktlint, Detekt, JaCoCo и bootJar успешны. Включён повтор исторического v4 receipt
  через Firebase с неизменными UUID, requestId и суммой. Уменьшение числа integration
  относительно T11 связано со снятием семи HTTP v1-suite (62 прежние проверки) и
  добавлением матрицы отказа старому токену, а не skip или ослаблением auth в тестах.
- После всех тестов исходные UUID, деньги, история и очереди Pixel совпали с приватной
  резервной копией. Изменилось только служебное lastSyncedAt; SQLite integrity OK.
  Настройки экрана восстановлены и проверены, приложение открыто в обычном режиме.
- Тестовый сервер и production автоматически не развёртывались. Перед реальной
  семейной приёмкой двумя Google-аккаунтами и проверкой отказа старому Bearer в Railway
  нужен deploy нового JAR. В текущей работе отказ подтверждён локальным HTTP/PostgreSQL
  набором; release-сертификат и свежий выбор Google-аккаунта на release APK отдельно.
