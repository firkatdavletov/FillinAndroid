# T05 — подключение существующего бюджета через Firebase

Актуализация T12: статический мобильный токен отключён. Текущая настройка, миграция
и выпуск описаны в [T12](firebase-static-token-retirement.md). Прежние статические
HTTP-сценарии ниже описывают исторические этапы и больше не используются.

## Уточнение плана

21 октября 2026 пользователь разрешил не поддерживать HTTP API v1–v3: приложение
ещё в разработке и используется одним тестовым пользователем. Новое Firebase-подключение
использует только v4. Совместимость старых HTTP-контрактов не добавлялась.
Существующие данные не удаляются; профиль или очередь прежнего формата останавливает
Firebase-обмен с понятной ошибкой, вместо скрытого преобразования или повторного списания.
В проверенной копии Pixel бюджет уже использовал v4, старые очереди отсутствовали.

## Доступно в Android

«Облако» показывает Google-аккаунт и полученные от сервера доступные бюджеты с названием
и ролью. Пользователь явно выбирает бюджет. Для первого запуска тот же путь доступен
через «Подключиться к существующему», без обязательного создания локального бюджета.
Вход сам по себе не присваивает бюджет аккаунту и не отправляет локальные операции.

Если UUID бюджета и memberId совпадают с текущей базой LEGACY, профиль привязывается
к UID на прежнем файле Room. Старый обмен останавливается до смены scope. История,
баланс, UUID, курсор и v4-команды остаются в той же базе; requestId и intent сохраняются.
Повтор v4-команды использует тот же серверный receipt и не меняет деньги второй раз.

Другой бюджет загружается в отдельную базу. Профиль становится активным после полной
загрузки всех страниц. Ошибка загрузки сохраняет текущий бюджет; повтор использует тот
же профиль. При выходе облачная база скрывается, данные сохраняются. Если прежняя база
LEGACY уже привязана, для локального режима используется отдельный файл; повторный вход
исходного UID восстанавливает выбранный облачный профиль.

Запросы Firebase используют свежий ID token. После первого 401 SDK принудительно
обновляет его и повторяет запрос один раз. При смене аккаунта ответ отбрасывается.
Токены не сохраняются в реестре профилей, очередях и WorkManager inputData.
Автоматический обмен непривязанного профиля требует Google-входа и явного выбора бюджета.

## Серверный контракт

- `GET /api/v4/budgets` — список бюджетов проверенного Firebase UID: `id`, `name`, `memberId`, `role`.
- `GET /api/v4/budgets/{budgetId}` — прежний `CloudBudget` со `scope`.
- `GET /api/v4/budgets/{budgetId}/sync/changes` — полный согласованный срез v4 и последующие изменения.
- `POST /api/v4/budgets/{budgetId}/sync/commands` — существующие v4-команды с неизменным расчётом receipt.

На каждом запросе Firebase Admin проверяет токен; приложение не передаёт доверенный UID
в теле запроса. Сервер выбирает `BudgetActor` по UID и budgetId, проверяет активное членство
и блокирует строку членства на время финансовой транзакции. Чужой UID и отозванный MEMBER
получают 403. Токен другого бюджета не разрешает подменить household/member в команде.

Миграция PostgreSQL V24 добавляет `firebase_budget_access` и название бюджета с безопасным
значением по умолчанию. Существующие UUID, авторство, суммы и receipts не переписываются.
Пара UID/budget уникальна; один memberId не может принадлежать разным Firebase UID.
Один UID может иметь несколько бюджетов. Создание нового облачного бюджета — T06.

## Настройка прежнего бюджета на Railway

Развернуть сервер FinanceConsultante с изменениями T05 и V24. В его Variables сохранить
действующие Firebase credentials/project ID и указать обе переменные:

```dotenv
FIREBASE_AUTH_ENABLED=true
FIREBASE_LEGACY_UID=<UID нужного пользователя из Firebase Authentication → Users>
FIREBASE_LEGACY_MEMBER_ID=<UUID прежнего активного участника бюджета>
```

Использовать точный UID, не email и не Telegram ID. `memberId` — уже существующий UUID;
нового участника для привязки создавать не нужно. Его можно получить на сервере запросом:

```sql
SELECT id AS member_id, household_id, role
FROM member
WHERE revoked_at IS NULL;
```

Выбрать участника нужного старого бюджета. При нескольких строках нельзя автоматически
привязывать первую. Частичная настройка UID/memberId отклоняется при запуске. При первом
запросе настроенного UID сервер идемпотентно связывает именно эту пару; совпадение email
другого аккаунта не даёт доступа. Пустая настройка не выдаёт прежний бюджет никому.
Настройка другого UID не перехватывает уже привязанный memberId.

Развёртывание production и изменение его данных не выполнялись в рамках T05.
По умолчанию установленная Android-сборка обращается к Railway; новые endpoints станут
доступны после обновления сервера. Без привязки список бюджетов аккаунта пуст.

## Проверка

Автоматические device-тесты используют отдельные базы и синтетические аккаунты/API.
Они проверяют сохранение прежнего файла и очереди, отказ другому UID, отдельную загрузку,
ошибку второй страницы и повтор после потерянного ответа. Unit-тесты HTTP проверяют
адрес v4, Bearer token, один refresh после 401 и неизменность тела повторной команды.
Серверные интеграционные тесты используют PostgreSQL/Testcontainers и stub Firebase verifier.
Настоящий Google-вход и проверка подписи Firebase были отдельно проверены в T03;
сквозная приёмка T05 с настоящим аккаунтом на обновлённом Railway выполняется отдельно.

```bash
./gradlew :app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb install -r -t app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb shell am instrument -w \
  -e class com.firkat.fillin.feature.budgetconnection.BudgetConnectionDeviceTest \
  com.firkat.fillin.debug.test/com.firkat.fillin.FillinTestRunner
```

Установку выполнять поверх приложения после приватной резервной копии. Не использовать
`connectedDebugAndroidTest` на личном Pixel: этот task может удалить приложение с данными.

Ручная приёмка после обновления сервера:

1. Открыть «Облако», войти нужным Google-аккаунтом, обновить список и выбрать старый бюджет.
2. Сверить баланс и историю. Добавить расход и выполнить синхронизацию.
3. Перезапустить приложение: бюджет и операция должны сохраниться.
4. Выйти, войти другим аккаунтом: прежний бюджет отсутствует в списке и локальные данные скрыты.
5. Вернуться исходным аккаунтом: восстанавливаются тот же бюджет и его очередь.

## Результаты 2026-10-21

- Android: APK и instrumentation APK собраны, 188 unit-тестов успешны.
- Pixel 10 Pro XL: полный прогон `OK (83 tests)`, из них 81 успешный device-тест и
  2 live Firebase-теста без opt-in пропущены. Пять новых сценариев T05 прошли:
  прежний файл/UUID/очередь и отправка расхода; чужой UID; другой бюджет в отдельной базе;
  потеря второй страницы; потеря ответа на команду без дубля денег.
- Сервер: `check bootJar` успешен; 315 unit и 270 integration-тестов без пропусков,
  PostgreSQL 17.11/Testcontainers, ktlint, Detekt, JaCoCo.
- Перед установкой создана приватная резервная копия Pixel и проверена SQLite integrity.
  После полного прогона суммы, история, UUID и очереди сверены с этой копией.
- Настоящий Google-вход не заменялся заглушкой в рабочем приложении. В новых тестах T05
  используются синтетические аккаунты/verifier/API; реальный сквозной сценарий на Railway
  требует отдельного развёртывания и указанных выше UID/memberId.
- Отдельный opt-in прогон `FirebaseLegacyBindingLiveTest` успешен: UID получен через
  настоящий Firebase SDK текущего аккаунта, прежние household/member сверены с действующим
  сервером через чтение метаданных v4. Финансовые команды не отправлялись. Значения для
  оператора сохранены в приватный файл вне Git; в логи и этот документ они не копируются.
  Без `prepareLegacyBinding=true` этот служебный сценарий пропускается.
