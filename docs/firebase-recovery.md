# T11 — выход, сбои и восстановление

## Поведение

Выход немедленно скрывает облачное содержимое через проверку текущего UID в
ActiveBudgetContent. Реестр сохраняет отдельный выбор для каждого аккаунта; файлы
и очереди не удаляются. Другой аккаунт не получает прежний каталог, профиль или worker.
Возвращение исходного UID восстанавливает его выбранный бюджет и неотправленные изменения.
Локальная работа не требует сети или входа.

Запросы Firebase закреплены за исходными UID и budgetId. Токен запрашивается заново
для каждого HTTP-запроса. После 401 выполняется одно принудительное обновление и один
повтор с прежним путём, requestId и payload. Смена аккаунта во время получения токена
или refresh запрещает следующий HTTP-вызов. Отменённый coroutine не отправляет запрос
после позднего ответа SDK. Ответ прежнего аккаунта не публикуется в новом контексте.

Повторный 401 показывает ошибку входа и сохраняет очередь; сеть и 5xx оставляют
изменения для повторного обмена с backoff WorkManager. Уход с бюджета останавливает
следующие запросы. Запрос, уже принятый сервером, может завершиться в исходном бюджете;
повтор после возвращения использует тот же requestId. Активная синхронизация и mutex
принадлежат конкретному runtime: быстрое возвращение к ещё занятому профилю не создаёт
вторую базу или параллельный обмен.

## Исправления T11

Ранее isSyncing мог остаться true в SQLite после остановки процесса. При первом
открытии нового runtime теперь сбрасывается только этот устаревший флаг и ставится
sync_interrupted. На экране доступен повтор и показано, что изменения сохранены.
Уже работающий runtime при переключении туда и обратно не сбрасывается. UUID,
payload/requestId, курсор, история и lastSyncedAt при восстановлении не переписываются.
Начальная загрузка, сетевой callback и открытие приложения продолжают планировать
обмен только для выбранного доступного облачного профиля.

Проверка UID и отмены теперь выполняется также после получения токена, непосредственно
перед первой отправкой и повтором после 401. Это закрывает промежуток, когда аккаунт
сменился во время ожидания SDK. Такое же правило действует для серверного профиля.

Очередь хранится в Room, а wirePayload фиксируется до отправки. После остановки
между серверным commit и локальным подтверждением повтор сохраняет финансовую
идемпотентность. Незавершённая многостраничная загрузка хранит staging и курсор;
восстановление публикует весь снимок атомарно после последней страницы.
Новых миграций, зависимостей, credentials или серверных endpoints в T11 нет.

Автоматические проверки используют синтетические аккаунты, изолированные Room-файлы
и API без обращения к рабочему бюджету. В фазах остановки процесса серверная фиксация
моделируется приватным тестовым журналом, переживающим процесс Android; реальная
серверная идемпотентность проверяется отдельными PostgreSQL integration-тестами.
Это не заменяет реальный Google-вход и ручную приёмку через тестовый сервер.

## Повтор на устройстве

1. Войти первым Google-аккаунтом, выбрать облачный бюджет и отключить интернет.
   Добавить расход, запомнить остаток и число ожидающих изменений.
2. Выйти: прежние облачные данные скрыты. Войти вторым аккаунтом: доступны его бюджеты.
   Вернуться первым аккаунтом офлайн: восстановлены его бюджет, расход и очередь.
3. Включить сеть, синхронизировать, затем повторить обмен. Проверить на втором устройстве:
   расход один, сумма не списана повторно.
4. Создать ещё расход и во время обмена сменить бюджет. Проверить, что данные другого
   бюджета не изменились. Вернуться и завершить исходную очередь.
5. Повторить с остановкой Fillin во время синхронизации. После запуска индикатор не
   зависает; при необходимости доступна повторная синхронизация. Остаток меняется один раз.
6. Для отказа сервера/истёкшего токена использовать только управляемое тестовое окружение.
   Проверить понятную ошибку, сохранность очереди и успешный повтор после восстановления.

Финальные APK устанавливаются через adb install -r. connectedDebugAndroidTest на личном
Pixel не используется, поскольку может удалить приложение. До установки создаётся
приватная резервная копия с проверкой SQLite; после тестов сверяются исходные таблицы.
Автоматический helper для реального process-restart не входит в рабочее приложение:
BudgetProcessRecoveryTest принимает t11Phase=prepare/recover и общий UUID t11Run.
Между фазами host ждёт приватный синтетический checkpoint и завершает процесс приложения.

Воспроизводимый запуск после установки обоих APK:

```bash
python3 scripts/check-budget-process-recovery.py --device DEVICE --adb /path/to/adb
```

Команда намеренно останавливает Fillin, сохраняет приватные логи и проверяет новый PID
в фазе восстановления. Предварительно нужно завершить текущую работу в приложении.

При отзыве MEMBER и повторном приглашении действует правило T10: прежний профиль и
очередь архивируются, а новое членство получает отдельную копию. Архивные команды не
переписываются на новый memberId и автоматически не отправляются. Интерфейс их ручного
восстановления не добавлен. Production и тестовый сервер автоматически не развёртываются.
