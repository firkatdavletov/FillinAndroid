# Одноразовые правила расходов: контракт backend

Android добавляет `ONCE` к `MONTHLY` и `WEEKLY`. Поддержка сервером пока не подтверждена; выпуск для синхронизируемых бюджетов необходимо согласовать с готовностью backend.

## Создание и чтение

Создание правила через существующий endpoint:

```json
{"categoryId":"category-id","amount":"100.00","frequency":"ONCE","startsOn":"2026-11-04"}
```

Для `ONCE` `scheduleValue` отсутствует; при чтении Android принимает отсутствующее поле и `null`. Для `MONTHLY` обязателен день 1–31, для `WEEKLY` — ISO-день 1–7. Остальные поля и ответы существующего API сохраняются.

Дата одноразового расхода равна `startsOn`, не раньше начала учёта бюджета и дня создания в Asia/Almaty. Для очереди offline-команд день создания — `authoredOn`, а не день доставки на сервер: задержанная синхронизация допустима. Прошедшие сохранённые правила не валидируются как новые.

## Синхронизация

Команда `CREATE_RULE` передаёт `frequency: "ONCE"`, `startsOn` и не передаёт `scheduleValue`. Снимки и изменения `RECURRING_RULE` возвращают эти значения; существующие сущности, версии и формат команды сохраняются. `UPDATE_RULE` продолжает менять только сумму (в протоколах с полным снимком содержит также поля существующего правила).

Сервер материализует ровно один `RECURRING_OCCURRENCE` на `startsOn`. Ограничение уникальности `(ruleId, dueOn)` и идемпотентность requestId предотвращают дубли при повторной доставке. Android использует локальный ID `ruleId@date` и при получении серверного расхода сопоставляет его по `(ruleId, dueOn)`, сохраняя канонический серверный ID и оплату.

Неоплаченный расход остаётся просроченным после своей даты. Расширение горизонта планирования, повторная синхронизация и перезапуск не создают новые расходы. Оплата, частичная оплата, закрытие, изменение суммы и удаление используют существующие контракты и правила; материализация не сбрасывает их состояние.

## Проверка совместимости перед выпуском

Проверить создание через API и очередь синхронизации, задержанную доставку после даты расхода, получение правил без scheduleValue и с null, повторную доставку, оплату и отсутствие повторной генерации. Старые клиенты без поддержки ONCE могут неверно трактовать периодичность: backend должен согласовать минимальную версию клиента или иной существующий механизм совместимости перед включением функции для общих бюджетов.

Полное редактирование в новом Android-редакторе расширяет прежний контракт изменения
только суммы. Новая семантика и зависимость облачного выпуска описаны в
[контракте редактора](backend-rule-editor.md).
