# Подтверждаемая связь фактических операций с планами

Статус: спецификация для реализации в FinanceConsultante. Этот Android change не меняет backend.
Сначала выпускается совместимый сервер, затем Android. Финансовая Room-база Android обновляется 4→5;
это не версия HTTP API. Firebase, budget-scoped v4 API и протокол страниц сохраняются.

## Поведение

Создание фактической операции само по себе не оплачивает план. Новые Android-команды
`CREATE_OPERATION` содержат `planMatchingMode: "CONFIRM_REQUIRED"`. Сервер сохраняет только
проводку и возвращает необязательное предложение. Отказ пользователя не требует отмены
проводки: команда связи вообще не создаётся. Подтверждение, замена и снятие связи — отдельные
идемпотентные команды. Операция может быть связана максимум с одним планом, план — с несколькими
операциями. Связь не создаёт проводок и не меняет фактический баланс.

Подбор в рамках бюджета и категории, с совпадающим типом EXPENSE/INCOME и валютой KZT:

1. Открытые просроченные планы по возрастанию срока: самый старый первым.
2. Планы на дату фактической операции.
3. Будущие планы по возрастанию срока.

При одинаковом сроке порядок детерминирован: UUID дохода либо `(ruleId, dueOn)` расхода.
Сравниваем с `occurredOn`, а не с датой HTTP-запроса. Даты относятся к Asia/Almaty.
Экранные фильтры периода и типа не участвуют. Не подходят архивные категории, отменённые,
явно закрытые и полностью выполненные планы. Для расходов учитываются существующие периоды
и проекции повторяющихся правил в действующем пятилетнем горизонте приложения. Правила
месячных/недельных дат совпадают с Android, включая последний день месяца.

Предложение ничего не резервирует и не изменяет. Перед подтверждением сервер проверяет
план повторно. Если он исчез, закрылся или изменился, сервер возвращает конфликт, а не
подбирает другой план. Android сохраняет фактическую операцию и предлагает выбрать заново.

## Согласование возможностей и совместимость

`GET /api/v4/budgets/{budgetId}` возвращает прежний `scope` и новое поле:

```json
{"scope": {"householdId":"…", "memberId":"…", "role":"OWNER", "accountingStartedAt":"…", "timeZone":"Asia/Almaty", "currency":"KZT"}, "capabilities":["confirmedPlanLinkingV1"]}
```

Новый Android передаёт `X-Fillin-Capabilities: confirmedPlanLinkingV1` в запросах бюджета,
changes и commands. Отсутствие/пустой capabilities в ответе означает отсутствие поддержки.
До отправки каждой новой команды создания или изменения связи Android проверяет capability
(один раз за обмен), сохраняет очередь и показывает `backend_update_required`, если его нет.
Нельзя молча игнорировать `planMatchingMode` и продолжать автоматическое сопоставление.

Серверная миграция сохраняет прежние принятые receipts/requestId и старые wire payload.
Повтор уже принятой команды возвращает сохранённый результат до проверки новой версии
финансового контракта, но после проверки Firebase-участника и принадлежности бюджету.
Ранее принятые автоматические связи не создаются повторно.

На сервере нужен признак включения нового поведения для бюджета. Первый успешно принятый
`CREATE_OPERATION` с CONFIRM_REQUIRED либо SET/REMOVE связи атомарно включает его. После
включения новые финансовые запросы и чтение sync без заголовка возможности получают
HTTP 426 `client_upgrade_required`: старые клиенты иначе ошибочно закрывают частичные доходы.
Сохранённые принятые receipts остаются повторяемыми. До включения поддерживаются прежние
команды без нового поля; миграция не переписывает их payload и UUID. Переход должен быть
согласован для всех участников семейного бюджета. Ответ capability означает, что сервер уже
реализует все описанные здесь проверки, расчёты и ограничения старых клиентов.

## Команды и ответы

Используются `POST /api/v4/budgets/{budgetId}/sync/commands`, Firebase ID token и прежние поля
`requestId`, `householdId`, `memberId`, `type`, `entityId`, `authoredOn`, `expectedToken`.
BudgetActor проверяется по UID, budgetId и членству, а не только по полям тела запроса.
MEMBER может изменять связи операций, которые ему разрешено изменять по действующей политике
владения операциями; создание/изменение самих правил и планов остаётся отдельным правом OWNER.

### CREATE_OPERATION

Дополнительное поле `planMatchingMode = CONFIRM_REQUIRED` обязательно для новых клиентов.
Не запускать сопоставление ни в контроллере, ни в сервисе проводки, ни в фоновых обработчиках.
Возвращается receipt с `requestId`, `revision`, `entityToken` и `suggestedPlan` либо null:

```json
{
  "requestId":"11111111-1111-4111-8111-111111111111",
  "revision":42,
  "entityToken":1,
  "suggestedPlan":{
    "target":{"type":"EXPENSE","planId":null,"ruleId":"22222222-2222-4222-8222-222222222222","dueOn":"2026-10-30"},
    "categoryId":"33333333-3333-4333-8333-333333333333",
    "categoryName":"Коммунальные услуги",
    "plannedAmount":"20000.00",
    "remainingAmount":"12000.00",
    "version":0
  }
}
```

Для дохода target содержит `type=INCOME`, `planId=UUID`, `ruleId=null`, `dueOn`.
Для расхода определяющая идентичность — `(ruleId, dueOn)`; `planId` необязателен и содержит
серверный UUID экземпляра, если он уже материализован. Строка Android `ruleId@dueOn` не UUID
и никогда не принимается сервером как occurrenceId. Сервер разрешает/материализует период
по паре и проверяет, что он принадлежит правилу. Новый материализованный период получает
начальную версию 0, как локальная проекция Android. `version` — версия конкретного плана/периода,
не версия повторяющегося правила. Денежные значения — точные десятичные строки KZT.

Android показывает локальное предложение сразу после локального сохранения. Серверное
предложение используется, только если локально кандидат отсутствовал и пользователь ещё
не принимал решения. Поздний receipt не отменяет отказ и не подменяет уже выбранный план.
Сервер сохраняет исходное предложение в receipt; идемпотентный повтор не выбирает новую цель.

### SET_OPERATION_PLAN_LINK

```json
{
  "requestId":"44444444-4444-4444-8444-444444444444",
  "householdId":"…", "memberId":"…",
  "type":"SET_OPERATION_PLAN_LINK", "entityId":"UUID фактической операции",
  "authoredOn":"2026-10-30", "expectedToken":1,
  "planTarget":{"type":"INCOME","planId":"UUID плана","dueOn":"2026-10-30"},
  "expectedPlanVersion":0
}
```

`expectedToken` — версия проводки. `expectedPlanVersion` — версия определения плана/периода.
Версия плана меняется при явном изменении суммы, категории, срока или статуса, но не при
изменении производного остатка от связанных оплат; это позволяет последовательно подтвердить
несколько частичных оплат офлайн. Изменение связи увеличивает версию операции и возвращает
её в `entityToken`. Полное выполнение проверяется по актуальным связанным суммам под блокировкой,
даже если определение плана не менялось.

Проверить POSTED-операцию EXPENSE/INCOME, валюту KZT, совпадение категории/типа, положительную
сумму после возвратов и доступность цели. Возврат не привязывается отдельно. Замена удаляет
прежнюю связь и создаёт новую в одной транзакции; прежний остаток восстанавливается.
Повтор запроса с тем же payload/requestId возвращает тот же receipt, без дополнительных связей.

### REMOVE_OPERATION_PLAN_LINK

Те же общие поля и `entityId/expectedToken`; target и expectedPlanVersion не нужны.
Снимает все прежние связи данной операции атомарно (включая сохранённые исторические связи).
Если связи нет, команда является успешным идемпотентным действием и возвращает receipt.
Не удаляет и не исправляет проводку.

### Ошибки

- 401/403: Firebase-авторизация, доступ к бюджету или право изменения операции.
- 409 `scope_changed`/`idempotency_conflict`: прежняя семантика, очередь не переписывать.
- 409 `version_conflict`: изменена операция; `plan_changed`: версия определения цели изменилась.
- 409 `plan_unavailable`: план отменён, явно закрыт, полностью выполнен или недоступен.
- 422 `invalid_plan_link`: неверные тип, категория, валюта, ссылка или неположительный вклад.
- 422 `unlink_before_category_change`: смена категории связанной операции без отвязки.
- 426 `client_upgrade_required`: клиент не заявляет поддержку активированного контракта.
- 429/5xx/потеря ответа: повторить неизменный requestId/payload.

Ошибки связи не отменяют создание операции. Клиент не делает автоматического rebase/reapply
подтверждения на другую версию или цель; пользователь выбирает план заново. В отличие от
проверки связи, обычные прежние v4-правки продолжают использовать действующую политику конфликтов.

## Схема, миграция и расчёты

Добавить следующую свободную Flyway-миграцию после реально установленной версии backend
(номер не резервируется этим Android change). Перед миграцией выгрузить аудит существующих
OCCURRENCE_PAYMENT/INCOME_MATCH: дубли одной пары, несколько целей одной проводки, несовпадающие
бюджеты/типы/категории, ссылки на отсутствующие строки. Противоречивые данные не удалять и
не переназначать автоматически; остановить миграцию с отчётом для явного исправления.

Нужен единый реестр `operation_plan_links` с ключом `(household_id, ledger_id)`, видом цели и
ссылкой либо на occurrence, либо на expected_income (CHECK ровно одной цели). Составные FK
проверяют принадлежность операции и цели тому же household; целевой тип проверяется сервисом
и ограничениями БД. Индексы — household+occurrence и household+expected_income. Перенести
существующие непротиворечивые пары без изменения ledger/plan UUID. Реестр — единый источник
для новых команд и старых backend-читателей; старые таблицы после переноса не должны оставаться
вторым независимо записываемым источником. Точные названия источников и DDL FK сверить с
FinanceConsultante при реализации; этот репозиторий не содержит его схемы.

Не хранить рассчитанный денежный вклад как неизменную сумму связи:

- Расход: `max(amountKzt − сумма POSTED-возвратов, 0)`.
- Доход: `amountKzt`.
- VOIDED/REJECTED проводки и неподтверждённые намерения не участвуют.
- Остаток: `max(plannedAmount − сумма вкладов, 0)`, BigDecimal/NUMERIC, без float.

Переплата не переносится ни в следующий период, ни в другой план. Связанный расход целиком
исключается из переменных расходов прогноза, как в текущем контракте; фактические проводки
и возвраты продолжают определять баланс независимо от связи. Снятие связи восстанавливает
его участие в переменных расходах, если нет отдельного VARIABLE_SPENDING_EXCLUSION.

Изменение суммы связанной операции и возврат пересчитывают остаток, сохраняя связь. Смену
категории запрещать до отдельной отвязки. Явно закрытый/отменённый план не открывается от
возврата; выполненность из суммы связей — производная и может измениться.
Сохранить все старые связи доходов и пересчитать их по суммам: прежний автоматически закрытый
план с полученной меньшей суммой снова имеет остаток. Не устанавливать специальный признак
полного исполнения для исторических доходов. Если старый backend сохранял производное закрытие
в статусе, миграция должна отличить его от ручного закрытия по существующей модели/аудиту;
не считать любое PAID ручным закрытием без проверки источника.

Обновить серверные списки/итоги/прогнозы: доходы показывают receivedAmount и remainingAmount,
в прогноз входит только остаток. Операция создания и предложение не уменьшают план.

## Синхронизация и доставка

Сохранить виды журнала `OCCURRENCE_PAYMENT` и `INCOME_MATCH`. В обоих `record.id` — UUID плана,
`record.ledgerId` — UUID проводки. Клиентский ключ записи — `id:ledgerId`, поэтому несколько
поступлений одного дохода не перезаписывают друг друга. Снятие связи публикует tombstone
с обоими полями. Замена публикует tombstone прежней пары и новую пару вместе с новой версией
LEDGER. При материализации расхода журнал также включает RECURRING_OCCURRENCE.

Все записи одной финансовой транзакции входят в согласованный срез. Пагинация может разделить
их по страницам, но верхняя ревизия среза фиксирована, и Android публикует его целиком после
последней страницы. Receipt revision покрывает все изменения команды. Не удалять локальный
overlay, пока соответствующий срез не импортирован.

Android сохраняет зависимости команды связи от создания/изменения операции и плана в Room.
Перед первой отправкой подставляет подтверждённую версию предшественника проводки, а для
локального дохода — receipt создания/изменения дохода. Версия правила не подставляется как
версия экземпляра расхода. Подготовленный wirePayload и UUID далее неизменны. Ошибка любого
родителя блокирует зависимую связь; независимые команды продолжают обмен. Замена локального
несохранённого намерения обновляет дополнительные зависимости, а не только одиночный predecessor.

## Проверки и порядок выпуска

1. На копии данных проверить аудит, перенос пар, уникальность и сохранность всех receipts.
2. Проверить создание без связи, все варианты подбора, partial income/expense, переплату,
   смену/снятие связи, изменение суммы, возврат, запрет смены категории и явное закрытие.
3. Проверить гонку двух участников: атомарный выбор, отсутствие двух целей у операции,
   отказ при закрывшейся цели, отсутствие молчаливой подмены.
4. Проверить lost response и повтор requestId, конфликт другого payload, несколько страниц,
   tombstones, backfill и последующий sync другого участника.
5. Выпустить backend с capability, затем Android. Отдельно проверить budget activation,
   отказ старому клиенту и повтор ранее принятой команды.
6. Проверить Android с сервером без capability: операция и очередь сохранены локально,
   автоматического сопоставления и потери payload нет.

Автоматического production-развёртывания нет. Сквозная проверка требует реализации backend;
Android-тесты используют синтетические бюджеты и ответы.
