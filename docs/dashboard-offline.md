# Главная из виджетов

Главная собрана из фиксированной конфигурации `DefaultDashboardWidgets` в двух столбцах:
«Общий баланс» и «Доступно для трат», затем «Дневной лимит» и «Прогноз остатка» (все 1×1).
Контейнер поддерживает 2×1 и 2×2; пользовательское редактирование
раскладки пока не реализовано. Увеличение системного шрифта увеличивает высоту рядов.

Каждый виджет — отдельная фича в `feature/dashboard/widgets` со своими use case, ViewModel,
UiState, Route и stateless Compose-компонентом. `DashboardDataSource` разделяет один поток
локального снимка между виджетами и координатором экрана. Подписка останавливается, когда
экран перестают наблюдать; возврат и жест обновления запускают перечитывание данных.
Сетевые ошибки не стирают локальные цифры; доступ учитывает `keepLocalAccess` протокола v4.
Пока бюджет не готов, цифры не показываются. Прогноз скрыт при отсутствии 14 завершённых
дней истории и сопровождается пояснением «Недостаточно истории».

## Локальные данные и история протокола v3

После первой полной синхронизации v3 Главная читает только Room. `DashboardRepository`
предоставляет `Flow<Dashboard>`; все карточки вычисляются из одного `BudgetContent` с
локальной проекцией категорий, планов и очереди команд. HTTP `/api/v1/dashboard` Android
больше не вызывает. Сетевые ошибки не блокируют уже загруженный бюджет.

Первая установка и обновление со схемы Room 2 требуют одной полной загрузки v3. Пока
она не закончена, финансовые итоги не показываются. Миграция 2→3 сохраняет операции,
категории, планы и обе очереди отправки; сбрасывает курсор/промежуточные страницы и
добавляет `local_operations.occurredAt`. Без destructive migration.

## Синхронизация

Чтение выполняется через `GET /api/v3/sync/changes`; курсор имеет отдельную версию v3.
Отправка фактических операций остаётся на v1, команд категорий и планов — на v2.
Помимо прежних сущностей сервер передаёт типизированные payload:

- `BUDGET_SETTINGS` / `budgetSettings`: `id` бюджета, `openingBalance`, `protectedReserve`;
- `SAVINGS_GOAL` / `savingsGoal`: `id` цели, фактический `allocatedAmount`;
- `VARIABLE_SPENDING_EXCLUSION` / `variableSpendingExclusion`: `id` проводки, исключённой
  из переменных расходов подтверждённым регулярным шаблоном.

Проводки дополнены `occurredAt`. Суммы — точные десятичные строки KZT. Новые записи
хранятся в `budget_sync_records`; удаления обрабатываются по `kind/id`. Все страницы
одной ревизии публикуются одной транзакцией. Backend с миграцией V21 и v3 endpoint
должен быть выпущен раньше этого Android-клиента. v1/v2 чтение сохраняет прежние наборы
типов записей для старых клиентов; автоматического отката нового клиента на v2 нет.

## Финансовые правила

`CalculateDashboard` повторяет необходимые показатели серверных `DashboardCalculator`,
`BudgetCalculator` и `BudgetForecastCalculator`:

- B = начальный остаток + проведённые доходы − расходы + возвраты на момент расчёта.
- R = остатки открытых обязательств до конца месяца, включая просроченные. Частичная
  оплата уменьшает остаток; явное закрытие убирает обязательство без новой траты.
- E = защищённый резерв; G = сумма фактических allocations целей. F = B − R − E − G.
- D включает сегодняшний день; дневной лимит = `floor(max(F, 0) / D)`.
- Месячные итоги и категории используют даты фактических операций. Возвраты не являются
  доходом, отрицательные чистые расходы сохраняются.
- Прогноз использует до 30 завершённых дней, включая дни без расходов, и требует не менее
  14 дней истории. Базовая дневная сумма округляется до сотых `HALF_UP`; осторожная сумма
  увеличивается на 20% с округлением `CEILING`, ожидаемые доходы сдвигаются на три дня.
- Из переменных трат исключаются связанные оплаты обязательств и подтверждённые
  регулярные расходы; возвраты следуют классификации исходной проводки.
- Показатель `budgetExecution` = неотрицательный факт + ожидаемые расходы до конца месяца.
  Проценты округляются до одного знака `HALF_UP`; при нулевом знаменателе процент отсутствует.

`PENDING` учитывается сразу, `REJECTED` и `VOIDED` исключаются. Ожидаемые доходы не
увеличивают B. Для локальных KZT-доходов используется серверный порядок сопоставления
с планом: ближайшая дата, срок, ID; сумма не ограничивает исполнение плана. После POST
доход временно имеет локальный статус `ACKNOWLEDGED`, чтобы сохранить сопоставление
до атомарного получения канонической связи и не вернуть его повторно в прогноз.

RUB-проводки используют сохранённую оценку `amountKzt`. Все деньги считаются через
`BigDecimal`; будущие взносы на цели и резервирование не считаются расходами.

Изменения Room, возобновление экрана и полночь в `Asia/Almaty` пересчитывают Главную.
Жест обновления запрашивает sync, сохраняя текущие цифры. При отсутствии `keepLocalAccess`
отзыв доступа или смена области очищает показатели; состояние синхронизации показывает общий `BudgetSyncPanel`.

## Проверки

Unit-тесты сверяют все поля с серверным контрольным примером, границы дат, возвраты,
нулевой бюджет, дефицит, классификацию расходов и локальные команды. Инструментальные
тесты проверяют поток Room, перезапуск, переход pending → acknowledgement → canonical,
публикацию страниц и миграцию с сохранением обеих очередей. Они используют синтетические
данные и отключённую автоматическую синхронизацию приложения.

Проверено 19 октября 2026: Android — 143 unit-теста, 43 инструментальных теста на
Android 16, `assembleDebug` и `lintDebug`; backend — `check` и `bootJar`, 308 unit-тестов
и 250 интеграционных тестов с PostgreSQL/Testcontainers. Ошибок и пропусков тестов нет.
