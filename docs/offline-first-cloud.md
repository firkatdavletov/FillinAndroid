# Offline-first и облачная синхронизация

Переход на Firebase выполняется по [поэтапному плану](firebase-auth-plan.md).
В T01 подключены SDK и конфигурация. В T02 добавлены [Google-вход и состояние аккаунта](firebase-authentication.md),
пока без серверной авторизации и привязки аккаунта к бюджету.
Настройка Firebase и проверки T01 описаны в [firebase-setup.md](firebase-setup.md).

## Первый запуск

Пока бюджет не настроен, доступны «Создать бюджет» и «Подключиться к существующему».
Создание сохраняет на устройстве начальный баланс KZT, дату начала учёта Asia/Almaty,
постоянные UUID и четыре базовые категории. Синхронизация выключена; сервер и токен
для локальной работы не нужны. Logout, удаление и смена бюджета не реализованы.

Подключение использует `API_BASE_URL` и `MOBILE_API_TOKEN` сборки. Приложение сначала
ищет существующий бюджет, затем загружает согласованный срез во временное хранилище.
Настройки сервера используются без дополнительного локального начального остатка.
Бюджет становится доступен после завершения загрузки. При `budget_not_found` показана
ошибка и остаётся выбор создания или подключения; серверный бюджет не создаётся.

## Облако

Вкладка «Облако» содержит состояние обмена, ожидающие изменения, последнюю ошибку,
дату и время последнего полного успешного обмена и три кнопки:
«Включить облачную синхронизацию», «Отключить облачную синхронизацию», «Синхронизировать».
Настройка переживает перезапуск. Отключение сохраняет данные, привязку, курсор и очереди;
планировщик и synchronizer проверяют разрешение до сетевых обращений.

Для локально созданного бюджета включение вызывает `POST /api/v4/budgets` с сохранённым
UUID запроса и неизменяемыми исходными настройками. Повтор после потери ответа возвращает
тот же бюджет. Если токен занят другим бюджетом, облако выключается с ошибкой; привязка
к нему автоматически не меняется. Включение после отключения продолжает прежний обмен.

## Данные и доставка

Room 4 отделяет `localReady` от `initialSyncComplete` и хранит `cloudEnabled`, `cloudBound`
и исходный payload создания. Миграция 3→4 сохраняет обе очереди, payload, зависимости и
подтверждения; сбрасывает только версионированный курсор и промежуточный срез. Уже настроенные
установки продолжают работать со своим бюджетом. Миграции 1→2 и 2→3 остаются доступны.

Новые команды операций, исправлений, возвратов, категорий и планов идут через общий
`budget_outbox` с зависимостями и порядком. Старый `operation_outbox` и ранее подготовленные
v2-запросы доставляются прежними контрактами без изменения payload. Редактирование и возврат
KZT работают локально, в том числе до отправки исходного расхода. Все суммы точные.

Обмен: pull → push → pull. Согласованный серверный срез и упорядоченная локальная проекция
дают данные всем экранам. Подтверждение старой команды не стирает более новые локальные
правки. Повтор команд безопасен по requestId. В v4 локальная версия побеждает конфликт
версий автоматически; новые серверные записи загружаются. Ошибки доступа и финансовой
валидации не обходятся и показаны на экране облака. Диалог выбора версии убран.

Новые операции поддерживают только KZT. Исторические RUB-записи сохраняются без переоценки
и показываются по сохранённой сумме KZT; их редактирование и возврат недоступны.

## Backend

Сначала требуется выпустить совместимый FinanceConsultante с Flyway V22 и v4 API:
`GET /api/v4/budget`, `POST /api/v4/budgets`, `GET /api/v4/sync/changes`,
`POST /api/v4/sync/commands`. Создание новых серверных бюджетов доступно через mobile API.
Telegram и загрузчик валютных курсов выключены в рабочих профилях; их исходники сохранены.

Новый mobile API требует только настроенный Bearer-токен. Привязка хранится сервером
по отпечатку токена, а мобильный участник не требует Telegram ID. Для прежнего бюджета
необязательный `MOBILE_API_TELEGRAM_USER_ID` однократно импортирует прежнюю привязку;
затем старые endpoints могут получить Telegram-идентичность из сохранённого членства.
Email-вход и выдача токенов не входят в эту версию. Production-развёртывание автоматически
не выполняется.
