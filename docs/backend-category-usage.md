# Синхронизация использования категорий

Android записывает одно событие после успешного локального создания операции. Время события фиксируется при сохранении, независимо от даты операции. Телефон считает частоту и формирует обе подборки. Сервер хранит и передаёт исходные события. Редактирование, удаление, возврат или серверное отклонение операции не меняют уже записанное событие.

## Доступ и хранение

Когда оба маршрута доступны, вернуть `categoryUsageV1` в `capabilities` ответа `GET /api/v4/budgets/{budgetId}`. Android объявляет поддержку в `X-Fillin-Capabilities`. Без capability Android копит события локально и продолжает основной обмен.

На обоих маршрутах обязателен действующий Firebase Bearer-токен и query-параметр `budgetId`. Найти членство по проверенному UID и ID бюджета. Из него получить `memberId`. Ответ содержит `scopeKey` в формате `<budgetId>:<memberId>`, как в существующем бюджетном обмене. Лента и её курсоры принадлежат только этому членству. Владелец семейного бюджета не получает доступ к лентам других участников.

Хранить события без изменений. Уникальные ключи включают `(budgetId, memberId, id)` и `(budgetId, memberId, operationId)`. Назначать каждому принятому событию серверную позицию в ленте. Позиции и курсоры должны оставаться безопасными при конкурентных вставках, чтобы поздний коммит не оказался позади уже выданного курсора. Удаление аккаунта или бюджета очищает соответствующие события. После импорта локального бюджета прежние ID бюджета и участника сохраняются и ожидающие события приходят через обычный POST.

## Загрузка событий

`POST /api/v4/category-usage/events?budgetId=11111111-1111-4111-8111-111111111111`

```json
{
  "events": [
    {
      "id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
      "operationId": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
      "categoryId": "bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb",
      "usedAtMillis": 1794124800000
    }
  ]
}
```

Принимать 1–100 событий. ID передаются каноническими UUID в нижнем регистре. `usedAtMillis` — целое неотрицательное число миллисекунд от Unix epoch UTC. Клиентское время сохраняется без переопределения. `operationId` и `categoryId` — ссылки для сопоставления на телефоне. Событие может поступить раньше записи операции или после архивирования категории, поэтому наличие этих строк на сервере не требуется.

В одной транзакции сохранить все новые события и подтвердить все идентичные повторы. Если тот же ключ уже связан с другим содержимым, вернуть `409 event_conflict` и не записывать ничего из пакета. При потере ответа клиент отправляет тот же пакет. Успешный ответ `200` содержит ровно один ID на каждое принятое событие, в произвольном порядке.

```json
{
  "scopeKey": "11111111-1111-4111-8111-111111111111:22222222-2222-4222-8222-222222222222",
  "acceptedIds": ["aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa"]
}
```

## Получение событий

`GET /api/v4/category-usage/events?budgetId=11111111-1111-4111-8111-111111111111&cursor=c1`

Без курсора вернуть первую страницу. Выдавать до 100 событий в порядке серверной позиции. `nextCursor` обязателен даже на пустой или последней странице. Следующий запрос с ним должен получить события после последней доставленной позиции. При `hasMore: true` курсор должен продвинуться. Клиент атомарно сохраняет страницу и курсор и объединяет события по ID. Порядок «Последние» определяется клиентским временем и ID события.

```json
{
  "scopeKey": "11111111-1111-4111-8111-111111111111:22222222-2222-4222-8222-222222222222",
  "events": [],
  "nextCursor": "c1",
  "hasMore": false
}
```

Для ошибок использовать JSON `{"code":"…"}`. Ответы `400 invalid_request`, `401 unauthorized`, `403 access_denied` и `409 event_conflict` сохраняют локальную очередь. Для просроченного курсора текущего членства вернуть `410 cursor_expired`. Клиент перечитает ленту с начала, сохранив локальные события. Курсор другого членства отклонять. Сетевые ошибки, `429` и `5xx` приводят к повторному обмену с задержкой. Основной обмен бюджета и запись операции продолжают работать при ошибках этого потока.
